## What an action is

Any consequential tool call becomes an action: tool name, sanitized arguments (credential-looking keys are stripped before storage), risk level, tenant/run/session attribution, approval policy, and expiry. Read-only tools may execute automatically; write tools need installation permission; destructive, financial, identity, email-send, and provisioning actions require approval by default.

## Lifecycle

```
pending → approved → executed | failed
pending → rejected | expired
```

Create with `POST /v1/actions` (idempotent via `Idempotency-Key`, scoped to your project — the same key elsewhere is a different action). Decide with `POST /v1/actions/:id/approve` or `/reject`. Both decisions are idempotent: replays return the recorded outcome with `deduped: true`. Terminal states conflict with `409`; expired actions return `410` and can never be revived.

## Delivery semantics: single-claim, at-most-once

Exactly one approver wins the `pending → approved` claim; that winner dispatches once, and concurrent approvers get the recorded outcome instead of a second side effect. This is **not** exactly-once external delivery:

- A crash between the external send and the result write leaves `approved` with no recorded outcome.
- Gmail does not accept our execution key as upstream idempotency.

On an ambiguous action, reconcile against the upstream outbox (Gmail sent folder, MCP server logs) before creating a **replacement action with a new key** — never reuse a key with a different body (that is `409 idempotency_conflict` by design).

## The action object

`POST /v1/actions` and `GET /v1/actions/:id` return the same object:

```json
{
  "id": "act_30dc90ba-...",
  "tool": "gmail.send",
  "risk_level": "write",
  "status": "pending",
  "arguments": { "to": "ada@example.com", "subject": "Your invoice" },
  "approval_policy": { "connection_id": "con_..." },
  "tenant_id": "ten_e9d4...",
  "run_id": null,
  "session_id": null,
  "expires_at": "2026-11-10T10:15:00.000Z",
  "approved_by": null,
  "resolved_at": null,
  "result": null,
  "error": null,
  "created_at": "2026-11-09T10:15:00.000Z",
  "updated_at": "2026-11-09T10:15:00.000Z"
}
```

`status` is one of `pending`, `approved`, `rejected`, `executed`, `failed`, `expired`. `tenant_id`, `run_id` and `session_id` say who the action belongs to; each is `null` when the action isn't tied to one.

## `approval_policy` on an action

On an action, `approval_policy` tells Cencori how to run the tool once it's approved. It does not decide whether approval is needed: every action waits for a decision.

| Key | Use |
| --- | --- |
| `connection_id` | The connection whose credential runs the call. Required for Gmail and for connector (HTTP) tools |
| `op` | For an imported connector operation: `{ "name", "method", "path" }` |
| `base_url` | For a connector call, when the connection has no `base_url` of its own |
| `mcp_server_id` | The MCP server to call |
| `mcp_tool` | The tool name on that server, when it differs from the action's `tool` |

With none of these, approving records the decision and runs nothing: you run the tool yourself. Actions that a run creates for a gated tool have these filled in already.

## Per-tool rules on an installation

Set `approval_policy` when you create an installation (or `PATCH` it later) to decide, tool by tool, what the agent may do for that tenant:

```json
{
  "approval_policy": {
    "default": "required",
    "tools": {
      "search_contacts": "auto",
      "gmail_*": "required",
      "delete_contact": "deny"
    }
  }
}
```

| Rule | Effect |
| --- | --- |
| `auto` | The tool runs without asking |
| `required` | A person approves each call before it runs |
| `deny` | The agent is never offered the tool |

- `tools` maps a tool name to a rule. A name ending in `*` matches every tool that starts with it. The most specific match wins: exact name, then the longest prefix, then `default`.
- `default` applies to every tool no entry matches, including the agent's system tools (such as ending the conversation). Leave it out to keep Cencori's own choice for those tools.
- Tool names are the ones you see in `tool_call.started` and `turn.paused`. An MCP or connector tool can be named by its own name (`send_email`) or by the full name the model sees (`mcp__9f8e7d6c__send_email`).
- Any other value is refused with `400 invalid_approval_policy`.

Without a rule, the tool's kind decides:

- The agent's own tools (webhook tools, system tools, apps connected on the agent) run without asking.
- MCP tools: read-only tools run without asking; anything else waits for approval. A server's `readOnlyHint` and `destructiveHint` annotations are respected.
- Connector operations: `GET` and `HEAD` run without asking; other methods wait for approval.

Rules apply from the next turn or run. A turn that is already paused keeps the rules it started with.

## Approvals in a session

A session turn does not wait in the open stream. When the model calls a tool that needs approval, the stream ends with `turn.paused` (`reason: "approval_required"`) and the session becomes `paused`. It stays paused for up to 24 hours at no cost.

```
event: turn.paused
data: {
  "reason": "approval_required",
  "action_id": "call_1",
  "actions": [
    { "action_id": "call_1", "tool": "gmail_send_email", "arguments": "{\"to\":\"ada@example.com\"}", "needs_approval": true, "runs_on": "cencori" }
  ]
}
```

Each action says who runs it:

- `"runs_on": "cencori"`: one of the agent's own tools, held by a `required` rule. Approve and Cencori runs it. This pause happens whether or not the turn set `pause_on_tool_calls`.
- `"runs_on": "client"`: your function tool, or an MCP or connector tool. You send its result. These pause only when the turn was sent with `pause_on_tool_calls: true`; without it the turn completes with the calls in its output.

`POST /v1/sessions/:id/approve` with the pause's `action_id` resumes the turn; the reply is a new stream that continues it.

- For `cencori` actions, send nothing: Cencori runs the tool and gives the model its result. `tool_results` can be left out when every action runs on Cencori.
- To decline one `cencori` action and let the rest go ahead, send a `tool_results` entry for it (`"The user declined to send this email."`). The tool does not run and the model is told what you wrote.
- For `client` actions, send a `tool_results` entry each, as before.

`POST /v1/sessions/:id/reject` declines the whole pause and ends the turn.

`POST /v1/actions/:id/approve` does not resume a session. It decides one action and, when the action is bound to a connection or MCP server, runs the tool and returns its `result`. To have Cencori run a paused MCP or connector call (`runs_on: "client"`):

1. On `turn.paused`, create an action for the call with `POST /v1/actions` (`tool`, `arguments`, `session_id`, and the binding in `approval_policy`). You receive `action.required`.
2. When a person approves, call `POST /v1/actions/:id/approve` and take `result` from the response.
3. Pass that result as the call's `output` in `POST /v1/sessions/:id/approve`.

## Approvals in a run

A run cannot wait for a person. An MCP or connector call that needs approval becomes a pending action (you receive `action.required`) and the run fails with `approval_required`; approve the action to run the tool. One of the agent's own tools under a `required` rule is not run, and the model is told why. Denied tools are refused in both cases.

Session approvals are mirrored into the actions index after the fact, so one timeline covers both. See [Tool calls and approvals](/docs/agents-api/tool-calls) for the full pause and resume reference.
